# 模型切换与 HDMI 显示完整优化计划

日期：2026-10-24

项目：D:\PLD / PYNQ-Z2，板端 192.168.2.99

状态：实施中（2026-10-25）；控制、自动显示、软件常驻及缓存候选已接入。尚未完成全部性能和物理验收，不将局部结果视为最终达标。

## 1. 问题和交付目标

用户当前实际体验：切换模型或者开启 HDMI 均至少等待约 30 秒；上传新图片、完成分割、切换模式后需要重复点击显示并等待。

这条反馈是本轮优化的主要问题。已有某些任务几秒完成的记录，不能反驳或替代用户从点击到模型可用、屏幕可见的完整体验。需要区分首次冷启动、同模型连续处理、显示后的推理恢复、模型切换四种状态。

最终目标：

1. 自动显示设置只需选择一次；新结果完成后自动上屏，跨模型和页面刷新保留设置。
2. 明显缩短点击到模型可用、点击到 HDMI 首帧提交和实际可见的时间。
3. 同模型连续推理复用已有计算资源；纯显示更新复用显示资源。
4. 明确控制 FPGA 所有权，减少重复启动和初始化，不允许计算和视频驱动错误地同时操作 FPGA。
5. 保留普通皮肤镜、皮肤镜 ROI、CAMUS、ACDC 的现有功能、结果文件和触控能力。
6. 修改集中于网页、应用控制、服务生命周期和显示适配，不修改模型数值、预处理口径、核心计算驱动、RTL 或位流。

本计划不承诺在实施前证明零缺陷；用小阶段、定向验证和逐阶段回退控制风险。第一阶段自动显示完成，不等于性能问题已经解决。

## 3. 能做与不能混淆的“常驻”

| 常驻对象 | 方案 |
|---|---|
| 统一入口、显示偏好、当前操作状态 | 优先常驻，并保存必要设置 |
| 已完成结果的引用 | 按模型及版本保存；切换回来可查看，不能当成新任务结果 |
| 纯 CPU 的模型元数据、已验证资源、软件模块 | 按收益和内存预算保留 |
| 当前模型的推理会话 | 无 HDMI/模型切换时持续复用 |
| 当前 HDMI 显示及触控会话 | 无计算资源交接时持续复用，支持画面更新 |
| 多模型的 DMA/CMA 缓冲和硬件驱动 | 不以全部同时驻留为默认方案 |
| 计算位流和 HDMI 位流同时保持有效 | 当前分离位流方案不支持 |

本轮所说的常驻是服务、软件准备和使用意图常驻；仍需正确释放实际硬件。在加载另一位流后，不得复用旧 MMIO、DMA、视频驱动对象。

当前板只有约 512 MB DDR，且 CMA 与普通可用内存不是同一预算。模型全部预热驻留不是第一方案，不能用总空闲内存推断 DMA 分配一定成功。

若最终要求“推理期间 HDMI 始终不断信号”，需要另立计算/视频共存的硬件设计或独立显示方案。本计划不通过修改现有位流解决它。

## 4. 用户操作行为合同

### 4.1 自动显示

- 统一入口提供“自动显示 HDMI”，本次升级初始启用；用户关闭后保存其选择。
- 设置保存在板端，由统一入口协调；浏览器 localStorage 只能用于显示缓存，不能作为唯一状态来源。
- 用户点击“停止 HDMI”时，同时关闭自动显示，取消尚未执行的显示请求。
- 分割成功并生成该视图所需文件后自动上屏；不得依赖网页轮询来触发。
- 显示失败保留成功分割及下载结果，提供只重试显示的入口，不重新推理。
- 无新结果时，切换模型不把上一个模型的画面作为目标模型结果展示。
- 切换回某模型可恢复其有效历史结果视图，必须标明“上次结果”；任务与模型/部署版本不一致则不自动恢复。
- 页面刷新或关闭不取消合法的板端任务和自动显示。

### 4.2 上传、分割和 ROI

- 提供“选图后自动分割”设置：皮肤镜与单图 CAMUS 可在输入完整且校验通过后自动提交一次。
- ACDC 必须等 ED/ES 等必需输入齐全，才可自动提交，不在选择第一个文件时启动。
- ROI 新图可自动生成一次初始分割；点、框和 ROI 编辑保留“运行”按钮作为确定提交动作。
- 拖动过程只更新提示，不逐帧触发推理；编辑期间不替用户连续排队计算。
- 新图重新生成 image token 并清除旧提示；保留自动显示设置，但不沿用旧图的分割结果。
- 普通皮肤镜与 ROI 切换属于工作视图切换，不应因此停皮肤镜模型服务或重载计算位流。
- 同一图片的 FG/BG/目标框修改继续复用有效概率缓存；新图、不同 ROI、模型或版本改变时按实际缓存合同失效。

### 4.3 连续任务

- 普通交互：一个任务完成后自动显示。
- 已有批量/评估任务：整个批次完成后显示最终结果，避免每帧计算和 HDMI 往返。
- 有新计算任务等待时，尚未开始的过期上屏请求可以被替换；已经开始的硬件切换必须按流程完成，不能强行中断释放。
- 不为本功能新增无限任务队列；保留现有单任务/busy 约束。

## 5. 状态与并发设计

### 5.1 分离三个状态

1. 计算任务状态：接收、计算、结果就绪、完成、失败。
2. 硬件状态：无所有者、计算准备、计算可用、显示准备、显示中、释放中、故障。
3. 显示意图：自动显示是否启用、目标模型、目标结果、视图、请求版本。

字段名沿用现有 API 风格，实施时定义兼容扩展；不能用一个 `ready` 或 `hdmi_requested` 同时代表所有含义。

### 5.2 核心流程

```text
新任务
  → 校验输入和当前模型
  → 如需 FPGA：取消过期待显示请求、关闭当前 HDMI、确认释放
  → 取得计算硬件并运行
  → 复制独立结果、生成所需视图、记录分割成功
  → 若自动显示仍有效且没有优先计算任务：释放计算资源
  → 获取显示硬件、提交首帧、更新 HDMI 状态
```

缓存命中的 ROI 更新可在现有 HDMI 运行期间只更新画面，不执行无意义的资源交接。

### 5.3 必须保持的约束

- 只有一个硬件所有者；所有启动、关闭、切换仍串行执行。
- 自动显示绑定模型、generation、job、图像 token/提示 revision 或对应任务身份。
- 任务完成时再次检查显示意图版本，防止用户停止后旧回调把 HDMI 打开。
- 模型切换后丢弃旧代际待显示请求，不能因旧任务晚到而覆盖目标模型画面。
- 重复显示相同结果和视图幂等；显示中切换视图走更新，不默认重建进程。
- 不在持有状态锁时执行长时间 HTTP 调用并等待反向回调，避免 entry/hub/worker 循环等待。
- 自动显示通过统一串行控制路径执行，不能从每个任务线程直接抢占硬件。
- 分割失败不自动上屏；显示失败不把已成功的分割改成失败。
- 仍保留硬件退出确认、故障状态和清晰错误信息，不通过缩短超时或忽略退出码“提速”。

## 6. 分阶段实施清单

### 阶段 A：完整计时和最小基线

修改：在现有入口、应用和显示适配层添加少量 monotonic 分段计时，使用现有日志/任务报告，不引入新监控系统。

时间点：

| 链路 | 时间点 |
|---|---|
| 模型切换 | 浏览器点击、入口受理、等待旧任务结束、显示释放、旧服务/会话释放、目标启动、目标硬件 ready、页面可操作 |
| HDMI | 点击/自动触发、控制端受理、等待原任务、释放计算、子进程入口、依赖导入完成、BaseOverlay 完成、视频配置完成、首帧提交、网页显示状态更新 |
| ACDC | 应用校验、原生库加载、其余导入、模型加载、辅助资源加载、硬件建立、数值自检、网格预热 |
| Skin8 | Core 准备、位流加载、会话构造、首次推理；细分只能在不修改核心行为的边界处测量 |

要求：

- 一个操作 ID 串联入口、服务和显示子进程；记录冷/热状态、原硬件用途、模型和结果 ID。
- 进程间用板端 monotonic 时间关联；浏览器使用自身 performance 时间，通过操作 ID 对齐，不跨时钟直接相减。
- 首帧提交与物理可见分开。物理可见用一次现场观察/录像确认，不把 ready 文件当显示器检测。
- 冷启动沿用现有日志作为线索；补齐计时后的启动只测需要定位的路径，不人为清缓存制造冷启动。
- 用户关心的 ≥30 秒路径至少取得一条完整轨迹；如未复现，保留计时等待实际操作，不用短样本宣布解决。

完成标准：能够解释主要等待段，标出未知区间和重叠区间；不把耗时字段简单累加制造假总耗时。

### 阶段 B：自动显示及错误分离

修改：统一入口持有显示偏好，应用任务完成通知控制层，控制层调度现有 HDMI show/stop；前端只展示状态和用户选择。

- 接入普通皮肤镜、ROI、CAMUS、ACDC 完成路径。
- 保留原 API，新增字段兼容旧页面，避免一次性改写全部网页。
- ROI 的计算完成与 HDMI 恢复异常分别记录。
- 完成回调放在计算资源可交接且 busy 状态处理明确的位置，避免自触发被自身 busy 拒绝。
- 对新图/新提示/切换模型/手动停止做身份校验和过期请求过滤。
- 保存自动显示、自动初始分割设置；不保存一次性授权 token 或可失效的硬件对象。

完成标准：下一张新图、跨模型、刷新/关闭网页后无需再次点击显示；手动停止始终有效；一次任务只自动提交/显示一次。

### 阶段 C：显示复用和反馈

修改：优先扩展现有显示适配，不另建覆盖所有功能的通用 GUI。

- 同一显示进程内更新结果或视图，保留 HDMI 配置和触控读取。
- 复用 ROI 已有状态同步；保留 ACDC ED/ES、切面、切层和普通四宫格功能。
- 相同 show 请求不启动第二个显示进程。
- 单纯隐藏画面可使用现有 blank 能力；需要计算位流时仍必须关闭视频硬件。
- 处理期间缩短必要状态反馈等待，空闲时恢复较低轮询频率；先复用现有 HTTP 方式，不为轮询优化新增 WebSocket 基础设施。
- 考虑在独立结果和 HDMI 所需文件就绪后提前显示，ZIP 继续在 CPU 侧完成。只有确认原计算路径不再访问 FPGA 才能交接；不能只看到一个 PNG 就提前切位流。
- ROI 现有 predictor 等后端完整 done 的路径，在计时证明文件打包占比明显后再考虑增加受控 result-ready 通知。

完成标准：纯显示操作不重新加载位流、不产生重复进程；上屏不妨碍原下载产物完整生成。

### 阶段 D：削减初始化和有条件的软件常驻

按阶段 A 的占比决定顺序，不对每条路径都添加缓存。

1. 优先减少无收益的重复构造、重复 show 和额外服务重启。
2. 入口启动恢复用户上次成功选择的模型，避免总是先冷启动 ACDC 再切到用户需要的模型。
3. 评估显示进程在关闭视频硬件后保留纯软件模块，恢复时重新创建正确的视频驱动。parked 状态不得保留活动 DMA、过期 MMIO 或阻止新所有者的硬件锁。
4. 评估 ACDC 应用暂停硬件、保留纯 CPU 软件状态，切回时只恢复必要硬件。应用退出仍可作为回退路径。
5. 校验和缓存按真实部署身份绑定。进程重启、文件版本变化和故障后必须失效；不直接删除校验、数值自检或降低就绪标准。
6. 软件网格预热可在同一未变更进程内复用；涉及新硬件配置的检查仍按原合同执行。
7. Skin8 软件准备缓存只在应用适配层可可靠实现且收益明确时采用；不为几毫秒收益侵入核心 FrameSession。

关键前置条件：当前控制层将 inactive/MainPID=0/cgroup 清空作为释放证据，Skin8 入口还持有进程级硬件锁。软件常驻不能只删 stop；必须定义“暂停并确认硬件释放”接口、锁交接及相应状态。接口未完成前保持原启停流程。

完成标准：减少被实测确认的重复开销；CMA、进程和文件句柄在交接后无持续增长；真实新任务仍可恢复推理。

### 阶段 E：皮肤镜/CAMUS 同位流快速切换候选

只针对两个模型共用当前 Skin8 位流的情况，不扩大到 ACDC。

- 校验位流版本、硬件 ABI、当前配置和所有者。
- 等待旧任务结束，关闭旧模型会话，确认不再访问旧缓冲区。
- 保留已加载的计算位流，在适配层创建目标模型会话并装载目标参数/描述符。
- 目标模型准备完成才更新 ready 和 generation。
- 若当前是 HDMI 位流、发生过硬件故障、配置身份不明或 ABI 不符，使用正常加载路径，不猜测复用。
- 不让两个服务同时持有 FrameSession；优先采用一个明确的串行所有者。

该阶段可能需要改变服务与硬件会话的组织方式，属于较高风险候选。若必须更改核心驱动或 RTL 才可可靠实现，先记录边界并另行确认范围；本轮不擅自扩大。

完成标准：皮肤镜→CAMUS→皮肤镜两个方向都正确，固定样例 head/标签与基线一致，参数不会串用。无显示介入时才评价同位流复用收益。

## 8. 性能指标与目标

### 8.1 计时口径

- T_model：点击切换至目标模型真实可接受任务；包含旧任务等待，但另报该等待，以免把业务执行时间误判成初始化。
- T_hdmi_submit：显示意图触发至首帧成功提交。
- T_hdmi_visible：用户点击至物理画面可见，独立记录物理证据。
- T_result_display：分割所需结果就绪至 HDMI 首帧提交。
- T_new_image：输入完整并提交至新结果可见；ACDC 按实际体数据单独统计，不与单张皮肤镜图混比。
- T_same_view：已有 HDMI 会话内切换结果/视图的延迟。

### 8.2 暂定优化目标

以下是实施目标，不是当前已达到的数字，也不是未测条件下的承诺。阶段 A 完成后用同输入、同冷热状态的基线确认可实现性；不能通过换小图、排除慢阶段或删除检查来达标。

| 场景 | 目标 |
|---|---|
| 用户操作到页面阶段反馈 | 约 0.5 秒内给出受理/忙碌/错误反馈 |
| 已显示同一结果的重复 show | 不重启硬件，约 1 秒内确认 |
| 已显示状态下纯视图更新 | 争取 1 秒内响应 |
| 已有软件准备后的 HDMI 恢复 | 争取首帧提交不超过 5 秒 |
| 独立 HDMI 冷启动 | 争取首帧提交不超过 10 秒；超过则继续定位具体主耗时 |
| 皮肤镜↔CAMUS 同位流热切换 | 候选目标不超过 5 秒，需阶段 E 证明 |
| ACDC 软件常驻后的切回 | 候选目标不超过 15 秒，受必要硬件恢复约束 |
| 仍需完整冷启动的路径 | 显著降低已确认的重复开销，并明确报告不可省部分，不宣称秒切 |
| 自动显示 | 成功任务无需重复点击；停止后不被旧回调重新开启 |

单次结果只能报告单次或短样本范围，不能称 P95。某条用户报告的 ≥30 秒路径若最终仍无明显改善，必须作为未解决项，不能仅以“自动点击已实现”关闭任务。

## 9. 有限且有效的验证

### 9.1 本地定向验证

复用现有入口、HDMI 生命周期和 ROI 测试，新增只覆盖真正改变的合同：

- 自动显示一次且只绑定当前任务；重复 show 幂等。
- 停止后旧完成回调不再启动显示。
- 切换后旧模型回调、旧 token/revision 不覆盖当前画面。
- 分割成功但显示失败，结果仍成功且可下载。
- 网页刷新不重复提交任务；ACDC 必需文件未齐不自动提交。
- 暂停/恢复失败保持错误状态，不让两个硬件所有者继续运行。

不编写只验证函数名、常量或实现文本的镜像测试；不运行与本次改动无关的 RTL 综合和整套数值长测。

### 9.2 板端最小验收矩阵

| 用例 | 关注点 |
|---|---|
| 皮肤镜固定图 A → 自动上屏 → 图 B → 自动更新 | 显示后的推理恢复、正确图像与结果绑定 |
| ROI 初始分割 → ROI 拖框运行 → FG/BG/目标框缓存运行 | 新 ROI 的 FPGA 交接、缓存路径持续显示、触控功能 |
| CAMUS 固定输入 → 上屏 → 新任务 | 参数与结果正确、自动恢复 |
| ACDC 一组代表性完整输入 → 上屏 → 后续推理恢复 | 应用/硬件恢复；必要时已有有效结果用于显示测试，避免重复完整体数据计算 |
| ACDC→皮肤镜→CAMUS→ACDC | 各类交接、设置保留、资源释放 |
| 若实施同位流快速路径，补 CAMUS→皮肤镜 | 快速切换反方向与参数不串用 |
| 任务结束前关闭自动显示或切换意图 | 过期回调不重新上屏 |
| 人为模拟显示启动失败一次 | 分割结果保留、显示重试路径；先软件注入，避免无必要破坏硬件状态 |

每个正常代表用例先运行一次；只在失败、明显抖动或最终候选需要比较时补测。过程中的普通静态/页面调整不反复执行全矩阵。

结果检查：固定输入尽量复用已有 head/标签哈希；有新运行时同时收集性能和正确性。物理验收集中确认画面、触控及显示后的推理恢复。记录 CMA 和进程在关键交接前后状态，不新增长时间压力测试。

## 11. 实施依赖与停止条件

顺序：A 完整计时 → B 自动显示 → C 显示复用 → D 初始化/软件常驻 → E 同位流候选。

- B 可先产生操作体验收益，但不能代替 A 对半分钟等待的解释。
- C 的纯显示复用可以先落地；涉及跨计算的进程常驻属于 D。
- D 先选择计时占比最大的路径。若需大范围重写才能得到很小收益，保留简单方案并报告剩余瓶颈。
- E 必须依赖明确的硬件所有权与暂停/恢复合同；没有这些前提不尝试跳过 Overlay 加载。
- 模型结果改变、CMA 不回收、推理恢复失败、触控失效或版本混用时，该候选不得正式采用。
- 如最终主要耗时来自必要的硬件重配置且软件优化不足，应给出实测下限和单独的硬件方案，不擅改当前核心。
