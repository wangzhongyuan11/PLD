# 4 FPS 推理与 5 秒网页交付：目标和现状

2026-10-14 用户明确两个新目标：**B 端从已解码原始 RGB 到独立 INT8 head 和二值掩膜的持续吞吐达到 4 FPS**；**单张图从开始上传到六张全分辨率 PNG 的 ZIP 可下载不超过 5 秒**。二值掩膜按最终模型`q>=-1`并强制补边为背景；可在B性能验证包装层生成，不改变给C的原始head ABI。六张 PNG 的文件类型、分辨率与解码像素必须保留。两个指标分别测量，不用 PL 时钟、HDMI 刷新率或网页轮询次数代替。

## 验收口径

| 指标 | 必须测量的范围与通过条件 |
|---|---|
| B 端 ≥4 FPS | 预先解码原始 JPEG 得到 RGB；计时从每张 RGB 交给 B 预处理起，到对应独立 head 和按阈值/有效区生成的二值掩膜交付止，包含量化/缩放、PS/DDR/DMA、PL 计算、结果拷贝与掩膜生成。连续处理冻结 dev638 所代表的原图尺寸分布，至少 1000 帧；按首帧进入到末帧掩膜交付的墙钟计算有效吞吐 ≥4 FPS，同时报告逐帧中位/P95、不同尺寸组和首帧。不能用只计卷积的核心 FPS 或预装量化张量代替。按原模型/阈值逐图输入、head和掩膜字节一致；另做 ≥600 秒长稳、三类故障及下一帧恢复。 |
| 上传到 ZIP ≤5 秒 | 从客户端开始提交原始图像的 HTTP 上传到服务器六张 PNG 和 ZIP 全部关闭、可由 API 下载，包含传输、请求排队、B 冷/热初始化、JPEG 解码、推理、轮廓、视图合成、PNG/ZIP。分别覆盖首次请求和预热后的请求，以及约 1 MP 和接近当前 3 MP 上传上限的真实 JPEG；每组交错重复，逐次耗时均 ≤5 秒并报告 P95/最大值。六张全分辨率 PNG 的解码像素、成员顺序、掩膜、面积与冻结基线一致；访问码、历史、DMA/HDMI 切换和回退仍须正确。网页客户端实际开始上传和可下载时间另记录，不能只用服务器 `processing_seconds`。 |

以上是**新增目标**。原阶段5的 ≥1 FPS、在线 P95≤1 秒只是旧里程碑，不足以判定本目标通过。`dev638` 是开发集，不称独立测试集；1000 帧含重复图像，不称 1000 张独立图像。

## 当前板上证据与差距

| 范围 | 现有结果 | 对新目标的含义 |
|---|---|---|
| B 冻结 125 MHz 版 | 1000 帧核心中位 0.700375 秒（约 1.42 FPS）；已解码 RGB→head 中位 0.758002 秒、P95 1.265720 秒。80/1000 帧超过 1 秒，全部是 >10 MP 原图；≤3 MP 的 590 帧在线 P95 0.775 秒。 | 4 FPS 要求有效间隔 ≤0.25 秒；当前软件/硬件组合距离目标约三倍，小图与大图须分组验收。 |
| B预处理与跨帧流水空间 | 冻结1000帧报告中预处理均值0.133789秒、P95 0.563214秒；PLGraph均值0.703186秒；两者目前在`infer_images.py`逐帧串行，在线B均值0.836975秒。JPEG解码均值0.510685秒，但按B口径另计。 | 预处理均值低于0.25秒，理论上可与下一帧PL工作流水重叠；当前实现没有此流水，且>10 MP个别帧约0.6秒会形成短暂排队。须在PL关键路径先降到0.25秒以下后，再用有界队列与独立head/掩膜所有权实测持续吞吐和尾延迟。JPEG解码若计入整机4 FPS则另有瓶颈，本指标不含它。 |
| PL 算术与字节串行下界 | 固定每帧`compute_cycles=32,096,576`，125 MHz时为0.256773秒；单算术通路即使忽略所有其他开销，最多约3.894 FPS。现有64-bit AXIS经`axis_byte_unpack`每拍只消费1字节，经`axis_byte_pack`每拍只生产1字节；LOAD与RUN命令互斥，RUN须算完整个tile后才输出。以当前9,695,112字节/帧计，计算与字节串行的不可重叠部分至少41,791,688周期，即0.334333秒/帧、最多约2.991 FPS；实测命令`core_cycles`合计42,507,391周期即0.340059秒/帧。125 MHz正式布线WNS仅+0.013 ns。 | 当前数据流不可能靠PS调用、DMA峰值带宽或缓存同步达到4 FPS；须同时改造卷积周期和单字节装载/读回，或证明真正跨帧并行。仅将时钟上调而跳过布线验收不可接受。当前两侧RAM为8-bit银行，物理64-bit AXIS不等于内部每拍8字节。 |
| 同进程三张 6648×4398 原图板测 | `infer_images.py` 一次建立模型和 overlay，随后连续三帧的输入/head SHA256 均与冻结参考相同；在线 B 为 1.437、1.305、1.313 秒，后二帧 PLGraph 为 0.719、0.721 秒，前处理为 0.586、0.592 秒。仅有一次 `startup_ready` 和一次设备关闭；测试后正式网页服务恢复 active/HTTP 200。 | 保留设备可省去网页每次约 0.8 秒模型校验与约 1～2 秒 overlay 初始化，但它**不改变在线 B 的大图计算/缩放耗时**，不能充作 4 FPS 成果。机器记录：`out/board_sync_20261012/batch_reuse_20261014_v1_reports.tar.gz`、`batch_reuse_20261014_v1_audit.json`。 |
| B 当前命令与数据流 | 同版 `fastq_profile_v2_20261013.json` 的一帧共175条命令、9,695,112字节：15次参数加载124,584字节，73次输入加载5,470,176字节，14次LUT加载4,352字节，73次RUN读回4,096,000字节。命令调用墙钟合计0.588475秒，其中RUN调用0.409625秒；整帧PLGraph为0.713245秒，命令外约0.124770秒。核心计算32,096,576周期。 | 每个tile经PS收集、DDR→MM2S→PL运算→S2MM→DDR→PS拼接，层间再发送，属于中间特征反复往返。`dma_seconds`合计0.409090秒包含RUN期间PL计算等待，与0.256773秒计算周期重叠，**不能相加**。优化应优先减少中间特征搬运和命令依赖，再优化PS收集/量化输入；仅缩短C调用封装不够。 |
| 现有六 PNG 网页 | 24 张交错真实 JPEG 的热请求：约 1 MP 图中位 7.101 秒；接近 3 MP 图中位 14.453 秒。后者扣除 B worker 请求和每任务运行包校验后，中位仍为 **9.888 秒**（最短 9.778 秒）。首次请求另有约 11 秒 worker 冷启动。 | 即使把 B 请求与运行包校验都理想化为零，当前大图的其余网页工作也超过 5 秒。B 加速不能独自达标；C 轮廓/视图/六 PNG 编码与上传/ZIP 路径必须一起优化，且输出合同不变。原始记录：`out/board_sync_20261012/png_worker_stress_v3_20261014.json`。 |

当前 B 预算为 ≤90 BRAM36、≤96 DSP、≤32,000 LUT，给 C 至少留 50 BRAM36、124 DSP、21,200 LUT；现有 B 用约 67 BRAM36、53 DSP、7108 LUT。不能简单复制三套 67 BRAM 缓存并称资源可行；更改预算须与 C 再确认。原题要求的 PL 后处理尚无 RTL/BD/板测，物理显示器未接，均不能用网页软件结果代替。

## 执行顺序与候选去留

1. **先剖析B同一帧的关键路径。** 沿`board/pl_graph.py`的tile收集与`board/tensor_accel.py`的`_load_parts`/`run`，按15层、命令、方向、字节与周期统计，标出PS拷贝、缓存同步、DMA等待、PL计算和结果拼接的依赖及重叠。用已解码RGB测1000帧；现有`cProfile`把硬件等待算进`native_control.execute()`，不能将其当纯Python开销。每项优化在同版位流、同图顺序下先做交错短测。
2. **优先处理B数据流。** 对73次LOAD_INPUT与73次RUN读回建立可复现的字节预算；先在独立候选中评估减少中间特征回DDR，或把8-bit内部银行/单字节包处理改为能真正按多字节读写的布局。只把外部AXIS改宽不会消除内部每拍1字节限制。相邻层tile在片上保留、层间LUT/Pool/卷积融合须证明halo、skip特征生命周期、层间尺度、-128拒绝、tile边界和最终head仍位精确，并核对≤90 BRAM36/≤96 DSP/≤32,000 LUT的B预算。当前同一核心的单一命令互斥，双缓冲/跨帧流水若需修改RTL和ABI，先定义所有权、完成标签、错误恢复与C兼容路径，不把两个独立DMA通道误当作已经可以并行运行两条命令。
3. **同时压缩B计算周期和主机准备。** `conv_tile_engine`的ISSUE→WAIT_MAC→QUANT/DRAIN→NEXT_PIXEL逐组串行，15层共540,672个8通道输出组；QUANT完成前不会开始下一组MAC。首先按层量化其中可被MAC/量化流水重叠的周期，必要时设计有标签的累加结果缓冲，保证INT32溢出、Q24 ties-even、写回地址与复位精确；旧位流的32.097M纯计算周期已经超过4 FPS的31.25M周期整帧预算。大图精确缩放候选至少覆盖`ISIC_0014688`、`ISIC_0014784`、`ISIC_0014833`和一张3～10 MP图；与板端Pillow 9.0.1及A的量化输入逐字节相同。已否决的Q22拆分v2在6648×4398图上比v1慢约1.9%。4 FPS按持续吞吐验收，允许实测有效的预处理/PL跨帧重叠，但须包含所有帧与结果所有权；无明显板上短测收益的候选立即淘汰。
4. **B改造独立验收后再推进C。** RTL变更须从源码重跑仿真、Vivado 2026.1布线后setup/hold/脉宽、资源/DRC、同源bit/hwh/xsa；板上逐层、dev638/1000帧与三类恢复门只对最终候选执行。B达标后再优化网页常驻设备、全分辨率轮廓、六PNG/ZIP；当前大图非B/运行包校验部分中位约9.89秒，至少须实测削减约4.89秒且还要给B、校验和上传留时间，B优化不能独自证明网页≤5秒。
5. **仅对最终整机候选做全门。** B同版dev638原图逐张输入/head/掩膜零差异、≥1000帧吞吐≥4 FPS及≥600秒长稳，短包/缺包/复位后正确恢复；网页同版本做首次和热态小/近3MP原图交错重复、逐次上传→ZIP≤5秒、六PNG解码像素/ZIP/历史/回退核对。未通过任何一项时报告剩余差距，不把局部微测换算为整机4 FPS或5秒承诺。
