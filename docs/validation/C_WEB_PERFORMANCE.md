# C 网页单图耗时：板上基线与优化验收

本记录针对 `display_web/` 的静态图像流程。用户点击处理到结果可下载，与 B 的 `online_b_seconds` 是两个不同口径：后者从已解码 RGB 进入 B 预处理到独立 INT8 head，排除 JPEG 解码、文件 I/O、C 后处理和 HDMI。当前网页还不是连续视频推理；不能用 HDMI 刷新率或 B 核心 FPS 代替网页完成帧率。

## 逐阶段工作与成功标准

1. **C 导出路径与计时。** 在保持掩膜、轮廓、面积、六张视图的解码后像素、1280×480 比较图及 ZIP 成员语义不变的前提下，优化 PNG 保存与已压缩文件打包。记录运行包校验、B 子进程、结果读取、轮廓、每张 PNG、ZIP、任务完成的独立墙钟时间；明确报告与网页 API 中哪些阶段可见。先用 1022×767、2125×1411 固定输入在同一主机交替重复前后测试，再上板同条件复测，报告中位数、尾部耗时、输出大小和像素 SHA256。主机数字不作板上收益。
2. **本地/板端版本对齐与实测。** 审查后合入板端前端差异，保留源图不变、上传副本转换提示及 C/B 合同；修正手动启动脚本与实际运行包的一致性。通过完整源码哈希和必要测试后，在隔离部署目录板测，再切换服务。保留旧部署可回退。用同两张原始 JPEG 记录网页任务完成、原始 head SHA256、C 输出像素和 HDMI 切换结果；不要在服务占用硬件时启动另一套 DMA 测试。
3. **B 冷启动与连续任务。** 新计时若确认每张图仍有约 14～15 秒子进程冷启动，拆分 Python 导入、模型校验、overlay 装载、DDR 分配、结果写出。评估不改变硬件所有权的持久计算进程或批量任务：HDMI 使用另一 bitstream，显示前必须有界退出/释放 DMA，返回推理时再装载计算 overlay。只有同条件板测、故障恢复和图像正确性通过才采用；不能因复用缓存跳过模型/部署一致性检查。
4. **B 在线尾延迟与整机验收。** 冻结版 B 的核心中位 0.700375 秒、在线 B P95 1.265720 秒，项目自定在线 P95≤1 秒尚未通过。若修改 B 算法、驱动或 RTL，按改动范围重新跑数值、故障恢复、dev638/1000 帧；RTL/时钟变更还需 Vivado 2026.1 布线后时序和配套 bit/hwh/xsa。最后分别报告 B 吞吐、网页单图完成时延、连续选图吞吐与 HDMI 提交耗时，不将静态图网页称为实时视频系统。

## 常驻 B worker 隔离板测（2026-10-13）

首轮候选的三张真实 JPEG 虽然 head 与六视图均与历史板测一致，但每帧后 worker 消失，三帧 `persistent_worker_startup` 分别为 9.591、9.670、9.593 秒，故**首轮失败**。根因是 Linux `PR_SET_PDEATHSIG` 跟随创建子进程的父线程，而原 worker 由逐任务线程启动；任务线程结束便终止了 worker。GLM 修复为由与服务同生命周期的专用 launcher 线程启动 worker，并加入 PID/存活计时。主机 41 项 C Python 测试、9 项 B 计时测试、JS 测试及打包清单检查通过。

### 热请求的剩余耗时

从上述四帧的 `inference/frame_000001.json` 与任务 API 同次计时进一步拆分：第二张小图的 B worker 请求为 3.445 秒，其中每次重新构造模型并核对清单 0.811 秒、解析 overlay 元数据 0.995 秒、下载 bitstream 0.396 秒、`PLGraph` 推理 0.732 秒；C 在调用前另做整包校验 0.759 秒，调用后读取结果与原图 0.183 秒、轮廓 0.558 秒、视图合成 0.369 秒。大图的 C 结果读取为 0.707 秒、轮廓 2.264 秒、视图合成 0.841 秒，PNG 保存仍是更大项。上述阶段存在包含关系，例如 B worker 请求**包含**模型构造、overlay 初始化、JPEG/预处理和推理，不能相加为总耗时。逐帧原始记录为 `out/board_sync_20261012/worker_v2_b_timing_*.json`。

源码路径还显示同一 JPEG 在一次网页任务中被多次解码：`Console.submit()` 的 `decode_upload()`先生成 RGB 供 C 输出；B 的 `infer_images.main()` 再从输入 JPEG 解码以保持 A 的预处理合同；C 的 `load_result(..., source)` 验证图片哈希后又调用 `read_rgb()`。可考虑让 C 复用已解码且 EXIF 方向一致的 RGB，同时继续校验原始 JPEG 哈希与尺寸；这只优化 C 输出，不替换 B 的冻结预处理。大图在请求线程启动前的上传校验/解码约 0.662 秒，B 自身 JPEG 解码约 0.278 秒，C 结果读取约 0.707 秒，但目前没有单独量到第三次解码的纯耗时，不能将 0.707 秒全算作可节省。

下一步先完成双线程 PNG 的真实 HTTP 对照；随后再分别评估 C RGB 复用、每请求模型重建和 overlay 重配。模型或 overlay 的跨任务复用必须保持部署文件校验、单一 DMA 所有权、任务间复位及 HDMI 换位流后的强制重配置；不能为了省去约 1～2 秒初始化就沿用状态不明的硬件。它们主要改善网页单图等待，**不会直接关闭**当前按预热图像到 head 定义的 B 在线 P95≤1 秒门；该门仍要靠大图缩放和 PS/PL 核心的独立验证。

### 最终 125 MHz 计算侧剖析

用修复版隔离包的最终 bit/hwh、模型 golden 量化输入及 `board/profile_cnn.py`，先预热一帧，再重复五帧并逐帧比较最终 head；五帧均通过。PLGraph 中位 **0.716059 秒**，五帧样本 P95 0.730053 秒（仅作定位，不能与1000帧稳定性 P95 混用）。每帧固定 **175 条命令**；命令事件的墙钟合计中位 **0.589375 秒**，其中 DMA 等待字段合计 0.409550 秒，`compute_cycles` 固定 32,096,576 周期，在125 MHz下为0.256773秒。DMA等待与硬件计算、命令墙钟互相嵌套，三者不可相加；PLGraph和事件墙钟差约0.127秒，包含张量拼接、tile准备等事件外PS工作。

按五帧层耗时中位，`decoder_blocks_2_0`约0.097秒，`decoder_blocks_1_0`约0.066秒，`decoder_blocks_2_2`与`encoders_0_2`各约0.065秒，前四层合计约0.292秒。mode5/mode6 的 RUN 命令分别占约0.188/0.132秒，相关输入 LOAD 分别约0.075/0.043秒，是下一次按命令/层短测的优先区。cProfile 将 `native_control.execute()`计入约0.377秒内部时间，但该函数包含 DMA/核心有界等待和缓存同步，**不能**把它解释成0.377秒纯Python开销。当前125 MHz正式时序WNS仅+0.013ns，任何RTL或时钟改动都须重新布线及同源bit/hwh/xsa、逐层/整网数值和故障恢复验证。机器证据为`out/board_sync_20261012/fastq_profile_v2_20261013.json`、同名`.profile.txt`及`fastq_profile_v2_audit_20261013.json`；剖析运行期间正式服务暂停，结束后恢复并返回HTTP 200。
