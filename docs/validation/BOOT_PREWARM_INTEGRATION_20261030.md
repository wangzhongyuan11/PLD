## 整合后的行为

入口服务每次启动时，沿既有 `_switch` 暂停/恢复流程顺序准备三个模型。软件进程可常驻，硬件所有权仍依次交接；每次初始化、等待、释放和失败路径继续使用现有后端接口。准备中 `/entry/status` 返回 `phase=preparing`、已完成模型、当前目标及预热耗时；页面隐藏模型 iframe，拒绝手动切换和经入口提交的请求。

每个中间步骤不改写 `last_model`，不恢复 HDMI。全程成功并确认 engine、web、hub 及两个双模型服务均在运行后，才开放默认模型页面，并按现有身份校验恢复显示。准备失败不会自动强制重试。刷新网页不会重复预热；重新启动入口服务会重新执行。

## 相对附件的必要适配

1. **先建立 ACDC 常驻服务。** 附件默认顺序 skin→camus→acdc 在全冷启动时，尚不存在 ACDC engine；既有 `_switch(acdc)` 无法确认其 resident_handoff，就会走停止 hub 的旧路径，使之前预热的双模型服务退出。集成版先初始化 ACDC：默认 ACDC 为 acdc→skin→camus→acdc；默认皮肤镜为 acdc→camus→skin；默认 CAMUS 为 acdc→skin→camus。完成计数按三种模型去重，最后恢复默认模型时页面明确提示。
2. **自动显示也遵守准备状态。** 单步 `_switch` 完成后内部 phase 暂时为 ready，外部快照仍为 preparing。DisplayControl 的任务通知、历史恢复和队列派发均额外检查 boot 状态，避免这段窗口启动 HDMI；准备开始时取消旧显示意图。
3. **保留 PR #18 修复。** GET 与 POST 的互斥边界、hub 提交占用保护、通知幂等与有限重试继续保留；打开自动显示开关仍只保存偏好，不恢复旧图。附件对旧设置接口的修改不直接覆盖主分支。
